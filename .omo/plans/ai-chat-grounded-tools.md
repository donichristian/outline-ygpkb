# ai-chat-grounded-tools - Work Plan

## TL;DR (For humans)
<!-- Fill this LAST, after the detailed plan below is written, so it summarizes the REAL plan. -->
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**Who this is for and what changes for them:** A member of a workspace using the AI chat panel. Today the assistant can only skim short excerpts of at most five documents, cannot be pointed at a specific document, cannot be narrowed to one collection, and cannot tell you whether its answer is actually supported. After this work the assistant can be pointed at a document, read that document, search a single collection, remember what it read, and show you when an answer has no source behind it.

**What you'll get:** Four capabilities that work end to end - summarise a document, run a scoped search, answer a question with a visible source, and recommend documents with a stated reason - plus the measurement that tells the operator how well the assistant is actually doing, and a record of what the assistant read that survives the answer and a reload.

**Why this approach:** Every new capability is one small, read-only server tool inside the existing frozen allowlist, reusing the search and authorization code the product already has. Nothing new is installed, the external agent interface is untouched, and the two behaviours that could quietly weaken the knowledge-base boundary (a client-supplied tool, an unverified prompt) are explicitly ruled out.

**What it will NOT do:** No new packages and no vector database. No write-capable tool and no client-supplied tool. No change to the external agent interface. No new documentation files. No vectorised or semantic search - the ranking stays lexical, deliberately, until the measurement says otherwise.

**Effort:** Large

**Risk:** Medium - the assistant's behaviour changes the moment a body-reading tool exists, and this deployment's model provider is a separate agent that may ignore instructions sent from this repo
**Decisions to sanity-check:** The assistant's instructions live in this repo but ship switched off. Uncited answers are measured and flagged, not blocked. A document body is capped exactly as the external agent interface caps it. What the assistant read is remembered, but only the names and links - never the document text itself. See "Scope" for the one design change that came out of the gap analysis after the brief was approved.

(2) The operator/admin who owns the model gateway, the workspace AI preference and the workspace content, and who needs to know whether the assistant is working. ### Must have
- A repo-side instruction layer, sent as the library's native system-prompt option, plain strings only, switched off by an operator flag that defaults to off, documented in `.env.sample`.
- AI retrievals recorded through the existing search-query audit table under a new AI source value, written by a committed, idempotent migration.
- A citation-miss measurement (how often an answer contains no source returned by a tool in that run) exposed as a structured server log, plus a visible marker in the client.
- One shared, authorized, capped document-body reader under `server/commands/`, used by the external-agent fetch tool with byte-identical output and by the new AI body tool.
- A new read-only `fetch_document` tool in the existing frozen allowlist, authorizing through the existing document loader, capped at 20000 characters by default and 60000 maximum, returning a `truncated` flag.
- A deterministic document-reference path: an explicit document reference on the request is resolved and authorized server-side, binds the body tool to that document for the turn, and drives the first tool call - so "summarise this document" does not depend on the model choosing a tool, while the grounding probe keeps running on the member's own text.
- `search_workspace` extended with an optional, authorized collection scope and a bounded result count.
- A new read-only `recommend_documents` tool returning relevance-ranked candidates, each with an explicit reason.
- What the assistant read persisted as a body-free digest (tool name, arguments, result identifiers, character count) in a dedicated column, so the member can see what was read and no document text is stored at rest or returned by the message list. The digest is display and audit data only - it is not fed back into the model's context, because the upstream window deliberately forwards only `user` and `assistant` rows and admitting a synthetic turn would widen that allow-list.
- Client affordances: a prefill-capable panel bridge, a document-scoped "Ask AI about this document" action, optional starter prompts, and the no-source marker.
- In-place updates to the two existing AI documents, including the seven known drift items.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- MUST NOT add any runtime dependency - no vector extension, no embedding client, no retrieval framework, no new npm package.
- MUST NOT add client-supplied tools, client-declared tool stubs, forwarded-property merging, or any other route behaviour the current security comment at `server/routes/api/ai/ai.ts:569-572` forbids. A server-side **binding** carried on the existing tool context is not a client-supplied tool: the request body never supplies a tool definition, name or schema, the bound document is resolved and authorized server-side first, and the frozen allowlist is unchanged - everything else that comment forbids stays forbidden.
- MUST NOT add a write-capable tool, a document mutation, or any side effect to the AI chat path.
- MUST NOT store retrieved document text in the database, and MUST NOT return it from the message list. The persisted digest carries names, links and counts only.
- MUST NOT change the external agent interface - its route, tool list, tool semantics, section matching, paging shape, or output bytes. The shared reader must reproduce its current behaviour exactly, including that its section match is by heading text while the new AI tool matches by heading anchor.
- MUST NOT change the `ai.sessions.*` / `ai.messages.list` public route names, and MUST NOT change the authentication type of any existing route.
- MUST NOT relax, widen or bypass the existing authorization path (`authorize`, the document loader, the filter authorizer, provider membership scoping). The new grounding source is only an additionally authorized document the member can already read, non-archived.
- MUST NOT remove or weaken the grounding gate's knowledge-base boundary, the archived-document filter, the in-flight lock, the rate limiter, the application-only authentication restriction, or the upstream-error sanitization.
- MUST NOT create a new markdown documentation file, and MUST NOT hand-edit the extracted translation catalogues.
- MUST NOT run a repository-wide format pass or touch files outside the ones named in a todo. The repository carries a large pre-existing format and lint baseline.
- MUST NOT change the ranking source. Relevance ordering stays lexical; popularity blending is out of scope and carries an explicit ceiling note.

- The whole branch is delivered as a pull request against `development`.
